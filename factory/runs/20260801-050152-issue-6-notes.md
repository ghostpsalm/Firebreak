## Note: Slice B premise is factually wrong

Verified by reading the vendored `rusqlite-0.32.1` source directly
(`inner_connection.rs:119`): `rusqlite::Connection::open` unconditionally calls
`ffi::sqlite3_busy_timeout(db, 5000)` on every connection, and `Store::open`
(`src/store.rs:29-30`) uses exactly that path. Issue #6's claim "no
busy_timeout/busy_handler is configured anywhere... SQLite's default 0 ms busy
timeout applies" does not hold for this codebase — busy_timeout is already
5000ms by default. Oracle's slice-1 test took ~5s wall time to observe red,
consistent with a real but 5s-bounded race, not an instant one.
Slice A is unaffected (Result propagation is needed regardless of timeout
value). Slice B needs an owner decision: drop it (already satisfied), make it
explicit for documentation/discoverability (no behavior change), or raise the
timeout beyond 5000ms if that's judged too short for analyze()'s ingest-loop
transaction (a different rationale than issue #6 states, closer to #7's territory).
